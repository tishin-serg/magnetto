# Правила работы с проектом Magnetto

Эти правила применяются ко всему репозиторию. Явные указания пользователя имеют
приоритет. Не запрашивай повторное разрешение на уже согласованные действия.

## Ветки и коммиты

- Перед работой проверь git status, текущую ветку и локальные/удалённые ветки.
  Сохраняй чужие изменения и файлы. Не включай их в коммит своей задачи.
- Каждую новую самостоятельную фичу, исправление или задачу по документации начинай
  в отдельной ветке до редактирования файлов. Не работай непосредственно в master.
  Уточнения и исправления той же задачи продолжаются в её существующей ветке.
- Формат имени ветки: MGB-NN, например MGB-06, MGB-07. Используй следующий свободный
  номер после максимального среди локальных и удалённых MGB-веток и записей истории
  в README. Перед выбором номера обнови сведения об origin, если он доступен.
  Не переиспользуй номера удалённых или уже выпущенных задач. После 99 используй MGB-100.
- По умолчанию создавай новую ветку от актуального master. Для задачи, зависящей
  от ещё не слитой фичи, можно использовать её ветку; укажи эту зависимость в описании PR.
- Уже существующую ветку задачи продолжай использовать. Формат feature/... для
  новых веток этого проекта не применяй: исторический стандарт — MGB-NN.
- Новые коммиты называй MGB-NN: <краткое описание результата>, например
  MGB-06: add download preferences and confirmation. Номер совпадает с веткой.
  Исторические сообщения не переписывай ради единообразия.
- Делай коммиты логическими порциями. Перед коммитом проверь staged diff и
  git diff --cached --check. Добавляй файлы своей задачи явно.
- Не коммить .env, ключи, токены, профили Telegram, скачанные фильмы, дампы,
  диагностические каталоги и временные сборки. Не удаляй такие пользовательские файлы.
- Завершая работу, сообщи ветку, коммит, результат проверки и статус push/PR/деплоя.
  Не называй локальную ветку опубликованной.

## Реализация и проверка

- Используй Java 21 и Maven Wrapper проекта.
- Выполняй проверки, соответствующие изменению. Для изменения логики перед слиянием
  или выкладкой выполни .\mvnw.cmd verify; не пропускай ошибки тестов или сборки.
- Для изменений Telegram-команд, подсказок, кнопок или настроек проверь сценарий
  в Telegram после выкладки согласованной сборки. Одни mock-тесты не заменяют такую проверку.
- Проверяй успешный сценарий и затронутые исключения: неверный ввод, пустую выдачу,
  отмену, повторное нажатие, принадлежность заявки пользователю.
- Не изменяй пользовательские настройки или активные загрузки ради теста.
  Используй разовые условия заявки. Если для проверки нужны временные изменения
  настроек, запомни исходные значения и восстанови их, не затирая более поздние изменения пользователя.
- Тестовую загрузку ограничивай по размеру; после проверки останови только свою задачу.
  В отчёте укажи, что создано и что осталось. Не заявляй проверку полной доставки,
  если проверены только выбор места и создание задачи.
- Для изменения только документации достаточно проверить ссылки, команды,
  факты по Git и diff; повторный запуск всех тестов без изменения кода не требуется.
- Дополняй README описанием поведения и историей изменений. Фиксируй существенные
  результаты живой проверки в docs/.

## Слияние и выкладка

- Перед слиянием подготовь обзор изменений, результаты проверок и актуальное
  описание PR. Действуй в рамках уже полученных указаний пользователя.
- Учитывай действующий CI/CD: push в master запускает тесты и production-деплой.
  workflow_dispatch также может развернуть выбранную ветку.
- Не делай push в master как будто это только сохранение кода: это ещё и выкладка.
  Обычный путь — ветка MGB-NN, проверка, PR, слияние в master.
- Для согласованной проверки в Telegram допускается выкладка зафиксированного
  коммита рабочей ветки до слияния. Отмечай её как тестовую выкладку ветки,
  а не как выпущенную стабильную версию.
- Развёртывай сборку из конкретного коммита, прошедшего проверки. Не выкладывай
  незакоммиченные изменения. Сохрани возможность отката и проверь здоровье сервиса.
- На сервере сохраняй .env и данные. Перезапускай только затронутые сервисы.
  Не заменяй настройки и не останавливай пользовательские загрузки без необходимости задачи.
- Правила номеров версий, тегов и записи релизов находятся в VERSIONING.md.
