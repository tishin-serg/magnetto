# Версионирование Magnetto

## Текущее состояние

На 6 сентября 2026 года в репозитории нет тегов, а список GitHub Releases пуст.
Версия приложения в pom.xml — 0.0.1-SNAPSHOT. Исторические ветки MGB-01…MGB-05
обозначают задачи/этапы разработки, а не версии приложения. MGB-06 продолжает
эту нумерацию и содержит подбор фильма с подтверждением.

Не назначай задним числом номера v0.1.0, v0.2.0 и т. п. прежним этапам без
отдельного решения. Их история сохраняется в README по датам и коммитам.

## Формат версии

Для следующих версионированных релизов используй MAJOR.MINOR.PATCH:

| Изменение | Что увеличивать | Пример |
| --- | --- | --- |
| Исправление ошибки без новой функции и несовместимости | PATCH | 0.1.0 → 0.1.1 |
| Новая функция с сохранением совместимости | MINOR, PATCH обнулить | 0.1.1 → 0.2.0 |
| Несовместимое изменение публичного поведения, конфигурации, данных или API | MAJOR, MINOR/PATCH обнулить | 1.4.2 → 2.0.0 |

До 1.0.0 проект считается развивающимся: согласованные несовместимые изменения
можно выпускать с увеличением MINOR, явно перечисляя их и порядок миграции.
Выпуск 1.0.0 означает принятие стабильных контрактов поведения и конфигурации.

Обычная документационная правка не требует отдельного повышения версии приложения.
Если в релизе несколько задач, выбери наибольший требуемый уровень изменения.
Номер MGB не определяет номер версии: один релиз может включать несколько MGB-задач.

Первый будущий версионированный релиз предлагается начать с 0.1.0. Это план,
а не уже существующий тег или утверждение о выпуске текущей ветки.

## Разработка и предварительные сборки

- pom.xml в разработке содержит следующую целевую версию с суффиксом -SNAPSHOT,
  например 0.2.0-SNAPSHOT.
- Выпущенная версия в pom.xml не содержит -SNAPSHOT, например 0.2.0.
- При необходимости кандидата используй 0.2.0-rc.1, затем rc.2 и т. д.
  В GitHub такой выпуск помечай prerelease.
- Для тестовой выкладки фиксируй ветку, полный SHA коммита и время.
  Выкладка MGB-ветки сама по себе не создаёт стабильный релиз.
- Не меняй номер версии автоматически при каждом коммите или создании ветки.

## Подготовка и выпуск

1. В ветке MGB-NN определи следующую версию по содержанию изменения.
2. Обнови версию приложения в pom.xml и запись предстоящего релиза в README.
   Укажи вошедшие задачи, поведение, исправления, несовместимости и миграции, если они есть.
3. Проверь ссылки на имя JAR во всех файлах. Сейчас 0.0.1-SNAPSHOT жёстко указан
   в Dockerfile.runtime, CI/CD, скриптах и документации. При первом повышении версии
   обнови эти места вместе либо введи единое стабильное имя артефакта.
   Команда для поиска: rg -n '0\.0\.1-SNAPSHOT|torrentbot-.*\.jar' .
   Изменяй только версию самого приложения, не версию Spring Boot parent или зависимостей.
4. Собери .\mvnw.cmd verify. Проверь затронутый пользовательский сценарий.
   В отчёте связывай сборку и проверку с конкретным SHA.
5. Подготовь PR и выполни согласованное слияние. Учитывай: текущий push в master
   автоматически запускает production-деплой. Отдельного деплоя по тегу пока нет.
6. После успешной выкладки, проверки здоровья и при необходимости Telegram-сценария
   создай аннотированный тег vMAJOR.MINOR.PATCH на проверенном коммите master.
   Пример формата: v0.1.0. Для кандидата: v0.1.0-rc.1.
7. В рамках согласованного выпуска опубликуй тег и GitHub Release с тем же номером.
   Локальный тег без push не считай опубликованным релизом.
8. Укажи в README фактическую дату выпуска, тег, SHA, MGB-задачи и результат проверки.
   Следующую разработку веди с новым -SNAPSHOT в отдельной MGB-ветке.

## История и откат

- Теги опубликованных релизов неизменяемы. Не переноси существующий тег на другой
  коммит и не используй force-push для его замены.
- Исправление выпущенной версии оформляй новой задачей и новой версией.
- При откате разворачивай сохранённую сборку известного коммита/тега; учитывай
  совместимость миграций БД и сохранённых данных. Откат выкладки не переписывает историю.
- Для исторических этапов без тегов указывай «без версии», ветку и контрольный коммит.
  Дату коммита нельзя выдавать за подтверждённую дату production-выкладки.
- Статусы в README: «в разработке», «проверено на сервере, не слито»,
  «слито, без тега» или «выпущено vX.Y.Z». Не заменяй один статус другим без проверки.
